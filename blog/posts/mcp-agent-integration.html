MCP for agent integrations

Published Oct 2025 · 10 min read

Model capabilities explicitly, wrap them in guardrails, and iterate until the behaviour is predictable. That is the whole method.

TL;DR

Why MCP?

Multi-capability prompts let you combine several tools or APIs into a single agent workflow. They decouple the tool function from the prompt, which gives you control over which functions get invoked and when. By modelling capabilities and their schema explicitly, you can enforce safety and keep the agent's reasoning aligned with the business logic.

This matters most when generative AI meets corporate systems. Explicit capabilities are what let you attach role-based access, audit logging and fallback steps — so that calling an external tool or updating data is something you can reason about afterwards.

A minimal example

Simplified pseudo-code for constructing an MCP and wiring in a tool function:

// Define the capability
{
  "name": "sendEmail",
  "description": "Send an email with subject and body",
  "parameters": {
    "type": "object",
    "properties": {
      "to":      { "type": "string" },
      "subject": { "type": "string" },
      "body":    { "type": "string" }
    },
    "required": ["to", "subject", "body"]
  }
}

// Compose the MCP prompt with the capability description
const prompt = `
You are an assistant that can only call the "sendEmail" capability.
If the user asks you to send a message, call the function with the right JSON.
`;

// Handler that executes the actual send...

Step by step

  1. Define each capability separately — input schema, description and constraints.
  2. Compose a prompt that lists the available capabilities and says when to call them.
  3. Implement handlers that validate input, call the API and return a structured response.
  4. Write guardrails so the agent cannot take an unauthorised action or pass a malformed parameter.
  5. Test with example conversations, and refine the prompt and handlers against what actually happens.

Treating tool integrations as explicit capabilities makes agents both more flexible and safer. You can add or remove one without rewriting the prompt, and usage and errors stay traceable per capability.

Securing it for your organisation

When the systems are sensitive, security is the design constraint rather than a later pass. Use role-based access so the agent holds only the privileges each capability needs. Validate every input against its schema and sanitise what comes back. Log and monitor in enough detail that misuse is visible.

It is worth building a sandbox where new capabilities and prompts can be exercised against synthetic data before they reach production. Problems found there are cheap; the same problems found later are not.
