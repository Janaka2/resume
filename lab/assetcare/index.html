AssetCare: from an idea to a live Kubernetes deployment.

A complete asset-maintenance application, designed, built, containerised, secured and deployed by one engineer, running today at assetcare.janaka.me. Java 25 and Spring Boot 4.1 behind an Angular 22 front end, Keycloak for identity, PostgreSQL 18, S3-compatible object storage, all on K3s with Helm, Traefik and Let's Encrypt on one Hetzner Cloud server. AI-assisted engineering accelerated the implementation, the investigation and the documentation; the architecture, the security decisions, the validation and the production delivery stayed engineering-led.

Why it exists

Not another CRUD demo. The whole production path, executed.

Most reference projects stop at "runs on my laptop". AssetCare was built to go the rest of the way: a real identity provider, migrations, container images that run as non-root, a Helm chart, a cloud server created from Terraform, Kubernetes, a certificate that renews itself, health probes, backups, and a public URL that a stranger can log into.

The domain is deliberately small. People own assets (a car, a boiler, a laptop), assets need maintenance on a schedule, and someone has to prove what was done and when. Small enough to hold in your head, rich enough to need every piece of a serious system.

What it demonstrates

  • Enterprise Java, current generation. Java 25, Spring Boot 4.1, Spring Security 7, Hibernate 7, Liquibase 5, clean architecture enforced by an ArchUnit test.
  • Cloud-native delivery. Multi-architecture images, a Helm chart, K3s, Traefik, cert-manager, Terraform, GitHub Actions with scans, SBOM and signed images.
  • Production discipline. Probes, secrets, rate limiting, security headers, audit trail, backup CronJob with a tested restore, a runbook written for the person on call.
  • AI as an accelerator, not a substitute. Coding assistants worked inside a repository with written rules, and every decision that constrains the system is an ADR a human signed off.

  • Switch to dark mode, narrow the window to phone width, go offline: the interface says so.

Architecture

One door, one writer, everything else replaceable.

Traefik is the only public entry point. The Angular SPA is static files behind nginx. The Spring Boot API is the only process that writes to the database. Identity is external. Attachments live in object storage. Every one of the stateful pieces can be swapped for a managed service by changing a Helm value, not code.

Security

The backend is the authority. The UI only shapes what it shows.

Identity and authorization

  • Keycloak issues OpenID Connect tokens; the SPA uses Authorization Code with PKCE; the API is a resource server that validates every JWT.
  • Every endpoint requires a valid token. Anonymous calls get 401, verified on the live host on 23 September 2026.
  • Roles from the token: USER sees own assets, AUDITOR reads everything and writes nothing, ADMIN manages configuration and can restore or hard-delete. One AuthorizationPolicy decides; controllers never check roles.
  • Ownership is checked per aggregate: 404 for what you may not see, 403 for what you may see but not change.

Edges and supply chain

  • The live front end sends a strict Content-Security-Policy, X-Frame-Options: DENY, nosniff, a Referrer-Policy and a Permissions-Policy (observed in the response headers).
  • Rate limiting on /api at the Traefik ingress; the API answers 429 with Problem Details if a per-user limit is hit.
  • Errors are RFC 9457 Problem Details. Updates need If-Match (428 without it, 409 when stale). Creates accept an Idempotency-Key.
  • Uploads: content-type allowlist, size limit, sanitised filename, bytes stored outside the database under a generated key, SHA-256 recorded.
  • Images run as non-root with all capabilities dropped; CI scans dependencies and images with Trivy and CodeQL, runs gitleaks over the full history, and the release is signed with cosign and carries a CycloneDX SBOM.
  • No secret in Git. Production secrets are Kubernetes Secrets created once on the cluster; the development credentials in the repository are labelled as such and were rotated on the cluster before the demo went public.

Testing and CI/CD

Nothing reaches main untested. Nothing reaches the cluster unsigned.

ci, on every push

  • Backend unit and ArchUnit tests, then integration tests against PostgreSQL 18 in Testcontainers.
  • Frontend lint, format check, Vitest unit tests, production build under budget.
  • Playwright end to end against the production frontend image with a real Keycloak and API; the same smoke test later runs against the deployment.
  • A backup, damage, restore drill: dump, break the database, restore, compare row counts.
  • Helm lint and template, the observability compose file, Terraform format and validate; image builds with a Trivy gate.

security, weekly and on change

  • CodeQL for Java and TypeScript.
  • Trivy on dependencies and configuration.
  • gitleaks over the full history.
  • Dependency review on pull requests; Dependabot keeps images and libraries current.

release, on a version tag

  • Native amd64 and arm64 builds, one manifest per image, pushed to GHCR.
  • Scan, SBOM, keyless cosign signature and build provenance.
  • The packaged Helm chart attached to the GitHub release. v1.0.0 shipped this way on 23 September 2026.

Infrastructure and operations

Rebuildable from files in the repository.

Infrastructure as code

  • Terraform (provider hetznercloud/hcloud) creates the CX33, a stateful cloud firewall that admits SSH from the operator's IP and HTTP/HTTPS from anywhere, a cloud-init ubuntu user with root login disabled, and nightly Hetzner server backups. The API token lives only in an environment variable.
  • K3s installed by one script; cert-manager with a staging issuer first, then production; DNS pointed at the server; the certificate went Ready and the padlock appeared.
  • Helm installs the release with production values and an existingSecret; the chart's probes, resource requests and limits keep the whole stack inside 8 GB with headroom.
  • Why Hetzner and not a free tier: the earlier Oracle Cloud Always Free attempt could not be created on demand. ADR-012 records the decision and its cost.

Day two

  • Health. Liveness and readiness probes drive restarts and traffic; only /actuator/health and /actuator/info are exposed through the ingress. Metrics and everything else stay inside the cluster. A one-command health script prints OK / WARN / FAIL for pods, probes, certificate, backup age and the HTTP checks, naming the runbook section for anything wrong.
  • Backups. A CronJob runs a compressed, checksummed pg_dump nightly at 02:30 UTC, keeps fourteen, and can upload to any S3-compatible bucket; Hetzner server backups give an off-VM copy. The restore is a script that CI rehearses on every run. Recovery objective of the reference deployment: 24 hours.
  • Runbook. Symptom, check, action, confirmation, including "the VM is gone": Terraform, install script, chart, latest dump, DNS, new certificate, under an hour once the VM exists.
  • Demo data. Seeded through the real API by a script, so every write is authorized, validated and audited like a user's; reset by giving the demo account a fresh identity.

Observability

Instrumented in production. The full stack is a profile, not yet deployed.

Running on the live server

  • Structured JSON logs where every line carries requestId, traceId and spanId; a request id enters with or comes back in the response.
  • Micrometer metrics (HTTP, JVM, GC, HikariCP, cache, business counters) on the internal /actuator/prometheus endpoint, not exposed publicly.
  • OpenTelemetry tracing instrumented through spring-boot-starter-opentelemetry; telemetry is exported over OTLP only when a collector is present.
  • Business audit events in the database, each with its request and trace id.
  • Liveness, readiness and dependency health groups, verified from outside.

Available as an observability profile

Prometheus, Alertmanager, the blackbox exporter, Grafana (a 22-panel dashboard in Git), Loki, Tempo and the OpenTelemetry Collector, with thirteen alert rules that each link to a runbook section. The profile starts locally with make observability and has Helm values for the cluster.

Status, honestly: it is not running on the production server. The 8 GB CX33 holds the core chart with headroom; the observability profile needs a larger node or a second server, which the project's production-gaps document records. It is architecture and configuration ready to enable, not a monitoring capability currently in operation.

The engineering journey

From a prototype to a public URL, in the order it happened.

  • 01 · Architecture and standards

    Decisions before code

    version matrix · ADRs · definition of done · clean architecture

    • Every version checked against its official release page. Eleven ADRs for the choices that constrain the future, from PostgreSQL to "archive instead of delete".
    • The dependency direction written as an ArchUnit test, so it is enforced rather than described.

  • 02 · Local environment

    Docker Compose for the stateful parts

    PostgreSQL 18 · Keycloak 26 with the realm · MinIO

    • The same images as production, in one command, so every laptop and CI run the same versions.

  • 03 · Data and migrations

    Liquibase changesets with rollbacks

    Hibernate validates the schema; nothing is created by the ORM

    • Audit columns and optimistic-locking versions on every entity; a full audit event for every write, in the same transaction.

  • 04 · Authentication

    Keycloak, OIDC with PKCE, a resource server

    roles USER · ADMIN · AUDITOR

    • The application never sees a password. One authorization policy, tested, decides what each role may do.

  • 05 · Backend and frontend

    The API and the Angular application

    Problem Details · If-Match · Idempotency-Key · CSV export · attachments · command menu

    • Search, filters, sort and paging in the URL; conflict detection; drafts and unsaved-change protection; dark mode and phone layout.

  • 06 · Testing and CI

    Tests at every level, then a machine that runs them

    unit · ArchUnit · Testcontainers · Vitest · Playwright · restore drill

    • Rehearsing the CI jobs locally found a critical Tomcat CVE, invalid Terraform, missing security headers and a production build blocked by its own CSP, before the first GitHub run.

  • 07 · Containers and registry

    Multi-arch, non-root images on GHCR

    amd64 + arm64 · Trivy · SBOM · cosign · provenance

    • v1.0.0 released with signed images and the packaged chart; cosign verify passes.

  • 08 · Infrastructure

    Terraform on Hetzner Cloud

    CX33 · cloud firewall · cloud-init · server backups

    • After the free Oracle Cloud path failed to produce a server on demand, the trial moved to a small paid VM. The chart, installer and images were provider-neutral, so it was a change of VM, not of architecture.

  • 09 · Kubernetes and Helm

    K3s, cert-manager, the release

    one node · Traefik bundled · probes · resource limits · secrets created on the cluster

    • The installer learned to open ports 80 and 443 only when the image's firewall rejects them, a difference between Oracle's and Hetzner's Ubuntu images found during the install.

  • 10 · HTTPS

    DNS, staging issuer, production issuer

    Let's Encrypt · HTTP-01 through Traefik · certificate issued 23 September 2026

    • Staging first, so a mistake does not burn the rate limit; then production, then the padlock.

  • 11 · Health verification

    Probes, smoke test, login

    liveness UP · readiness UP · database reachable · anonymous 401 · Keycloak discovery 200

    • The same checks are repeated below, as run from outside the server.

  • 12 · Live

    assetcare.janaka.me, with a public demo account

    showcase data seeded through the API · development passwords rotated on the cluster

    • A stranger can log in, change data, upload a file and read the audit trail of what they did.

AI-assisted engineering

AI increased the velocity. Engineering discipline made it production-worthy.

This project was also an experiment in how far AI-assisted engineering can accelerate a senior engineer without removing the discipline. The answer was: a long way on implementation, investigation and documentation, and not at all on the decisions that decide whether a system deserves to be in production.

What the assistant accelerated

  • Architectural exploration. Options for identity, persistence, state management and object storage drafted against a model, then decided and recorded as ADRs.
  • Code generation inside written rules. The repository's CLAUDE.md states the non-negotiables: dependency direction, migrations only as changesets, archive instead of delete, an audit event for every write, Problem Details, authorization as a policy. Project skills (/add-feature, /add-migration, /write-adr, /architecture-review, /operate, /release) encode the playbook the assistant follows.
  • Debugging and migration analysis. Spring Boot 4.1 start-up failures (ambiguous CORS and upload-size beans), a lazy-association failure on list endpoints, an inject() after await that froze the SPA at "Loading", Keycloak's iss parameter left in the URL.
  • Kubernetes and deployment investigation. The iptables rule position that failed on Hetzner's image, a MinIO image tag that could not be pulled, a race in docker compose up --wait, a backups volume that had to be bound at install for helm --wait to succeed.
  • Tests, documentation and operations text. Test scaffolds, the setup guide written for a beginner, the runbook, the health script, dashboards and alert rules.

What stayed with the engineer

  • Architecture and trade-offs. One modular service before microservices, PostgreSQL before Oracle, Keycloak, K3s on one small server and the documented seams to an enterprise platform.
  • Security. The threat model, the authorization model, the header policy, the decision to pin Tomcat for three critical CVEs that the Spring Boot BOM did not yet manage, the rotation of the development passwords before the demo went public.
  • Validation. Every check in the verification report was run, and anything not run is marked as not executed. A reference nobody has run is a hypothesis.
  • Production decisions and delivery. Moving off the free tier that could not deliver a VM, when to tag v1.0.0, what to expose through the ingress, what a public demo account may and may not do.
  • Verification. Reading the generated code, running the tests, watching the certificate go Ready, checking the 401 from outside.

What it is not

A production-style reference deployment, not an enterprise platform.

The point of the project is the honest boundary. The application code is written so that an enterprise replaces the pieces on the right without a rewrite; the reference deployment deliberately stops short of them.

  • One node, one disk. A VM failure is an outage. No pod disruption budgets, no multi-zone, no autoscaling turned on.
  • Keycloak runs in development mode in the chart, with its realm imported from Git. Production mode on PostgreSQL is an open item.
  • Secrets are Kubernetes Secrets, created once on the cluster, not sourced from a vault.
  • The observability profile is not deployed on the 8 GB server (above).
  • Container root filesystems are writable; the Security tab reports it and the fix is documented.
  • No customers, no user numbers, no availability figure. It is a demonstration with a shared demo account and sample data, and it is described as such everywhere.
