Core mental model

Prompt engineering today is interface engineering. You are not only asking a question. You are defining:

  • the job,
  • the allowed inputs,
  • the rules,
  • the output contract,
  • and how correctness will be checked.
A good prompt should feel like a small technical spec, not a vague request.

The 5 building blocks

Role

Who the model should act like in this task. Example: “Senior Java architect.”

Goal

What success looks like. Example: “Find the root cause and produce the smallest safe patch.”

Context

Trusted facts, code, rules, schemas, requirements, logs, or business constraints.

Constraints

Hard boundaries. Example: “No invented APIs. Keep changes backward compatible.”

Output contract

Exact structure expected. Example: JSON, diff, checklist, ADR, or table.

Instruction hierarchy

Modern model families use instruction hierarchy. Higher-priority instructions override lower-priority ones. That is why your app-level rules should live in higher-authority messages, while untrusted content should be treated as data, not as instructions.

Higher authority
- Platform / root rules
- Developer / system instructions
- User request
- Tool outputs, retrieved docs, pasted content
Lower authority
Never mix user text or retrieved text into the same block as your trusted rules. That increases prompt injection risk.

Why hallucinations happen

  • Missing data: the model has no real evidence.
  • Rewarded guessing: your prompt forces an answer instead of allowing “unknown”.
  • Retrieval noise: RAG returns irrelevant chunks.
  • Schema pressure: the model tries to fill all fields even when evidence is missing.
  • Long-context failure: important facts are buried in the middle and get missed.

Best general template

ROLE
You are a senior software engineer working in <stack>.

GOAL
Solve: <clear task>.

CONTEXT (trusted)
- Environment:
- Constraints:
- Existing behavior:
- Success criteria:

INPUT (untrusted)
<<<
paste user text / logs / docs / code here
>>>

RULES
- Do not invent facts, APIs, files, endpoints, or commands.
- If information is missing, say exactly what is missing.
- Keep assumptions explicit and testable.

OUTPUT
1. Brief answer
2. Findings
3. Proposed fix / plan
4. Verification steps
5. Risks / assumptions
