# Discovery: search, structured data, llms.txt, public JSON

Strategy: make the pages excellent and plainly structured; everything else is a derived convenience. Google's AI
features and other AI retrievers build on the same crawl, index and quality signals as classic search, so there is
no separate "AI SEO" layer here, and no page exists only for machines.

## Public resources

| URL | What | Generated by |
|---|---|---|
| https://janaka.me/robots.txt | allows all, disallows `/partials/`, points at the sitemap | hand-written |
| https://janaka.me/sitemap.xml | every indexable page, git-based `lastmod` | `gen-sitemap.py` |
| https://janaka.me/feed.xml | Atom, 30 newest blog/academy/lab entries | `gen-feed.py` |
| https://janaka.me/llms.txt | short Markdown map of the site ([llmstxt.org](https://llmstxt.org)) | `gen-public-data.py` |
| https://janaka.me/llms-full.txt | the map plus experience, certifications, education, project detail, every page summary | `gen-public-data.py` |
| https://janaka.me/api/public/v1/index.json | catalogue of the JSON below | `gen-public-data.py` |
| https://janaka.me/api/public/v1/profile.json | identity + experience, certifications, education parsed from the visible CV | `gen-public-data.py` |
| https://janaka.me/api/public/v1/projects.json | products and reference projects | `gen-public-data.py` |
| https://janaka.me/api/public/v1/projects/{slug}.json | one project | `gen-public-data.py` |
| https://janaka.me/api/public/v1/resources.json | articles, Academy and lab pages with descriptions and dates | `gen-public-data.py` |
| https://janaka.me/assets/content-index.json | the site-search index (internal shape; use `resources.json` externally) | `gen-content-index.py` |

The JSON is static (GitHub Pages has no server), read-only and public. There is no `?q=` search endpoint and no
OpenAPI document, because there is no HTTP API to describe; search happens client-side (site search overlay,
`search_site` WebMCP tool). Every document carries `apiVersion` and `canonical` (the human page it represents).

### Shapes (apiVersion 1)

```jsonc
// profile.json
{ "apiVersion": "1", "canonical": "https://janaka.me/",
  "person": { "id", "name", "jobTitle", "positioning", "description", "url", "image",
              "location": { "locality", "country", "workRadius": [] }, "contact": { "email", "page" },
              "sameAs": [], "languages": [{ "code", "name", "level" }], "knowsAbout": [], "cv": { "page", "pdf": { "en", "de" } } },
  "experience": [{ "period", "location", "title", "organisation", "highlights": [], "technologies": [] }],
  "certifications": [{ "group", "name", "issuer", "status": [], "evidence": [] }],
  "education": [{ "institution", "degree", "period" }] }
// projects.json → { apiVersion, canonical, projects: [ <content/projects.json entry> + "api" ] }
// resources.json → { apiVersion, canonical, resources: [{ url, path, title, section, sectionName, description,
//                    tags, published, updated, readingMinutes }] }
```

Adding a field is compatible. Renaming or removing one needs `api/public/v1` → `v2` (keep v1 until nothing uses it).

### Privacy guard

`gen-public-data.py` `assert_public()` refuses to write keys like `phone`, `password`, `token`, `secret`,
`credential`, and values that look like phone numbers, `tel:` links, the AssetCare demo password, private keys or API
tokens. The validator re-checks the committed files. The phone number stays on the human contact card only.

## Structured data

One generated block per page (`<script type="application/ld+json" data-generated="gen-structured-data">`), built
from `content/*.json` and the page's own title, description and image:

| Page | Nodes |
|---|---|
| `/` | WebSite `#website`, ProfilePage, Person `#me` (full), SoftwareApplication/SoftwareSourceCode per project |
| `/resume/` | ProfilePage, Person `#me` (full) |
| `/products/` | ItemList of the products |
| a project's page (`/lab/assetcare/`) | SoftwareSourceCode for that project |
| Academy and lab resource pages | TechArticle (unless the page declares its own Article/Course) |
| every page except `/` | BreadcrumbList (Home › section › page) |

Hand-written blocks remain for blog posts (Article with `datePublished`), the AssetCare case study (TechArticle) and
the Course pages; their author/publisher/provider reference `{"@id": "https://janaka.me/#me"}`.
Entity ids never change: `https://janaka.me/#me`, `https://janaka.me/#website`, `<page>#<slug>`.

What is intentionally not marked up: ratings, reviews, prices, FAQ, HowTo, Organization (there is none), employer
relations (the CV text is precise; a `worksFor` triple would flatten "UBS via Cognizant").

## Canonicals and duplicates

Nine near-duplicate Linux handbook pages under `academy/modules/2026/FSE/` point their canonical at the fuller
copies under `FSE/Linux/` and are listed as `aliases` in `content/site.json`, so they stay reachable but never enter
the sitemap, feed, index or llms.txt. Internal links point at the canonical copies.

## After deploying: manual checks (Search Console)

Code cannot replace these; do them once, then monthly:

1. Verify ownership of `https://janaka.me/` (DNS TXT or HTML file) in Google Search Console, and in Bing Webmaster
   Tools (which can import from Search Console).
2. Submit `https://janaka.me/sitemap.xml`; confirm "Success" and the discovered URL count (~77).
3. URL-inspect `/`, `/resume/`, `/products/`, `/lab/assetcare/`, one blog post, one Academy page: "URL is on Google",
   user-declared canonical = Google-selected canonical, page fetched and rendered with content.
4. Inspect one alias (e.g. `/academy/modules/2026/FSE/awk-sed-mastery.html`): Google should select the `FSE/Linux/`
   canonical.
5. Enhancements / structured data reports: Breadcrumbs, Profile page, Articles; fix any errors at the generator.
6. Rich Results Test on `/` and a blog post.
7. Performance report: watch queries for role + location + stack; Core Web Vitals report for mobile.
8. Never commit Search Console credentials or verification secrets beyond the public verification token.
